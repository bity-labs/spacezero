# Local Host Startup

The current Local Host is a separate Node process managed by Electron Desktop. It runs only as a development Local Host today; packaged launch is still deferred.

## Current startup path

```txt
Electron main
  -> Local Host supervisor
  -> normal Node child process
  -> protected bootstrap/lifetime file descriptors
  -> Workspace Host HTTP server on 127.0.0.1:random
  -> supervisor capability
  -> renderer client capabilities via preload
```

## Step by step

1. Electron main creates a Local Host supervisor before opening the app window.
2. The supervisor resolves the Workspace Host executable.
3. In development, the executable is `apps/workspace-host/dist/main.js` run with Node `22.23.1`.
4. Electron starts the Host as a normal child process, not Electron Node mode and not `utilityProcess`.
5. Bootstrap material is sent over protected inherited file descriptors, not command-line arguments, URLs, logs, or renderer IPC.
6. Workspace Host consumes the one-time bootstrap secret.
7. Workspace Host starts an authenticated loopback HTTP server on `127.0.0.1` with a random port.
8. Workspace Host sends a ready frame back to Desktop.
9. Desktop exchanges the bootstrap secret for a Host-lifetime supervisor capability.
10. Renderer calls preload when it needs a Host connection descriptor.
11. Desktop uses its supervisor capability to mint a short-lived scoped client capability.
12. Client Runtime uses that descriptor for authenticated HTTP/SSE calls.

## Development Node executable resolution

The dev Local Host must run with Node `22.23.1`. `resolveLocalHostExecutable`
(`apps/desktop/src/main/local-host/local-host-executable.ts`) resolves which
Node binary to launch in this order:

1. `SPACEZERO_DEV_NODE_EXECUTABLE` — explicit override; the real-host E2E
   suite and CI use this to pin the Node under test.
2. `npm_node_execpath` — set when Electron is launched from a pnpm/npm
   lifecycle context.
3. `node -p process.execPath` fallback — resolves the `node` first on `PATH`
   and uses its real `execPath`.

The fallback exists because `electron-vite dev` does **not** inherit
`npm_node_execpath`: Electron is spawned outside the pnpm lifecycle, so the
environment variable is absent and the Host previously failed closed with
`LocalHostUnavailableError` on every renderer `spacezero:get-local-host-connection`
call. Repeating the resolution through `PATH` keeps `pnpm dev` working when
Electron is launched directly.

The resolved binary is validated before use:

- absolute POSIX path that exists on disk;
- `node --version` must report exactly `v22.23.1` (repo pin, matching
  `engines` and the packaged private Node); and
- the Workspace Host entry must exist under `apps/workspace-host/dist`.

Any failure throws `LocalHostUnavailableError` and the supervisor schedules a
bounded-backoff restart instead of starting a wrong-version Host. The PATH
fallback and the explicit-override order are covered by
`local-host-executable.test.ts`.

Practical notes:

- If `pnpm dev` reports `Local Host unavailable`, check `node --version` first;
  a PATH Node that is not `v22.23.1` reproduces the failure.
- `nvm`/version-manager users must have the pinned Node active in the shell
  that runs `pnpm dev`, or set `SPACEZERO_DEV_NODE_EXECUTABLE` explicitly.

## Capability ownership

- Electron main owns the supervisor capability.
- Renderer receives only short-lived scoped client capabilities.
- Client capabilities are held in memory and refreshed through preload.
- Host endpoints validate bearer token scope and allowed renderer origin.

## Restart behavior

Desktop restarts unexpected Local Host exits with bounded backoff. The Host reconciles unfinished Project Sessions on startup, but ambiguous turns or external side effects are not automatically replayed.

## Known gap

Packaged Local Host resolution still fails closed. Public builds still need private Node packaging, integrity checks, production dependency pruning, and Electron fuse hardening.
