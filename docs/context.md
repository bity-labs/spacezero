# Space Zero Project Context

## Purpose

Space Zero is an agentic desktop workspace for software builders.

The product exists to help builders plan, code, debug, manage knowledge, and ship software from one clean desktop GUI with minimal context switching.

## Product Thesis

Current AI building workflows are fragmented across AI chats, IDEs, terminals, browsers, docs, issue trackers, logs, and deployment tools. Space Zero should keep the builder's full working context in one place: code, agents, live sessions, skills, running app previews, debugging information, voice input, GitHub state, and project knowledge.

Space Zero owns the **builder-workspace layer**, not the agent-routing layer. The workspace, memory, and task-to-ship loop are the product. The agent harness is an implementation detail.

## Primary User

The primary user is a software builder who uses AI agents while building applications. They need to supervise agent work, inspect running apps, edit code, review diffs, manage GitHub work, and retain project context without constantly switching tools.

## Product Shape

- A real desktop GUI, not a terminal-first or TUI-first app.
- A polished project/session workspace inspired by tools like Conductor, Devin, VS Code, and Zed.
- Project sessions are first-class, with live sessions visible in a dedicated app surface.
- Editing, navigation, diffs, terminal/session output, browser preview, and debugging should converge in the desktop app.
- Pi is the default agent harness for v0.1.
- Project Session execution runs in a separate Workspace Host; Electron Desktop is a client and native platform adapter.
- v0.1 initially implements a Desktop-managed Local Host. Space Zero-managed Remote Hosts are planned for later.
- GitHub integration is first-class: issues, sessions, branches/worktrees, commits, PRs, reviews, and statuses should connect into one workflow.

## Important Distinctions

- **Desktop vs Workspace Host:** Electron Desktop owns windows, secure preload APIs, native integration, updates, and Local Host process management. The Workspace Host owns the Project catalog, Project Session execution, Pi, Session workspace files, Session Git operations, and durable Session state.
- **Native folder selection vs Project registration:** Desktop may select a folder through a native dialog, but the Workspace Host canonicalizes, validates, authenticates, and persists the Git Project. Desktop never maintains a duplicate Project database.
- **Electron runtime vs Local Host runtime:** Desktop uses Electron, while the packaged Local Host runs under private Node.js `22.23.1`. Workspace Host ships as compiled ESM with pnpm-pruned production dependencies, signed immutable resources, and an integrity manifest rather than an initial bundle. Public builds do not use `ELECTRON_RUN_AS_NODE` or Electron `utilityProcess` and disable unnecessary Node-mode/Node-options fuses.
- **Host Protocol implementation vs wire contract:** Effect HttpApi and Effect HTTP Client implement HTTP/JSON commands, queries, and authenticated typed SSE. Wire values remain plain interoperable JSON, HTTP errors, headers, and SSE fields; Effect runtime values, raw Pi events, and Electron types never cross the boundary. Generated OpenAPI is a derived artifact.
- **Session journal vs Session projection:** The Session Event Journal is the authoritative history for Host-owned agent Sessions, including Project Sessions and Global Chat Sessions. Relational projections are query-optimized and rebuildable from durable events; clients consume projections plus cursor-based event catch-up.
- **Session journal vs Pi transcript:** The Session journal owns stable Space Zero product history. Pi transcripts remain private Pi Adapter data for harness context and recovery and are never client contracts.
- **Durable events vs live deltas:** Meaningful Session boundaries and bounded content checkpoints are durable and advance the Session cursor. Provider token fragments and transport heartbeats may stream live but do not become individual durable events.
- **Bootstrap vs supervisor vs client capability:** A one-time secret passed through a protected child-process channel establishes a Host-lifetime supervisor capability held only by Electron main. Main mints short-lived scoped client capabilities held only in renderer/Client Runtime memory. The renderer never receives supervisor authority.
- **Local Host startup vs account activation:** Desktop may start the Local Host before Space Zero Account activation for readiness, but workspace access remains blocked until account activation is valid. The Local Host must not receive account secrets or refreshable account session material; it may receive only non-secret account/activation status needed for feature gating.
- **Local bootstrap vs remote authorization:** Local and future remote clients use the same short-lived scoped client-capability semantics after authentication, but credential issuance differs. Electron main bootstraps Local Host supervisor access; future account, pairing, or control-plane flows authorize remote clients.
- **Space Zero Account vs GitHub repository access:** A user may use GitHub OAuth as a Space Zero Account identity method without granting repository access. The UI should present account sign-in, GitHub identity, and GitHub repository access as distinct states so “signed in with GitHub” is not confused with selected-repository authorization.
- **Renderer vs main process:** Renderer code is UI. Electron main owns only desktop-native capabilities and the secure connection to the Local Host; it is not the owner of Project Session execution.
- **Terminal emulator vs terminal process:** `@xterm/xterm` and `@xterm/addon-fit` provide terminal display, input, and responsive sizing in the renderer; they do not create a shell. A future Terminal implementation places PTY-backed shell processes on the Workspace Host that owns the workspace. Its authenticated bidirectional transport requires a separate protocol decision because ADR 0026 deliberately excludes Terminal from initial HTTP/SSE.
- **Agent harness vs product layer:** Pi powers agent execution, but users should experience Space Zero as a workspace, not as a thin CLI wrapper.
- **Project tools vs Workspace Tools:** Pi's built-in project tools operate only inside the Project Session's authenticated managed worktree through the Host-side Pi Adapter. Space Zero Workspace Tools operate Space Zero product behavior through Host-owned typed services and safety policy. Neither domain routes privileged Session behavior through Electron main.
- **Agent Definition scopes:** The archived v0 scope and precedence design is retained only as research input. Agent Definitions are deferred for v0.1; scope discovery, project trust, selection, and precedence require an explicit reintroduction decision.
- **Agent Definition vs Session:** An Agent Definition is static reusable configuration. An initial Project Session is one live workflow with one Pi conversation, one Session Event Journal, and one managed worktree; Agent Definitions are deferred until selected for reintroduction.
- **Project Session vs Global Chat Session:** A Project Session is tied to a registered Git Project, managed worktree, branch, source revision, and project-scoped agent workflow. A Global Chat Session is not tied to a Project, worktree, branch, source revision, or Git lifecycle.
- **Session vs Chat Context:** Project Sessions and Global Chat Sessions directly own one conversation each. A separate Chat Context identity, `/clear` within one worktree, and conversation history rotation are deferred.
- **Multiple live Sessions:** The Workspace Host may run multiple Project Sessions and Global Chat Sessions concurrently. Active UI focus is not a runtime ownership boundary. Each Project Session retains its own event aggregate, Pi conversation, worktree, and branch; each Global Chat Session retains its own event aggregate and Pi conversation without worktree or branch identity.
- **Project Session isolation and source identity:** Every new Project Session uses a dedicated centralized managed Git worktree and branch created from the registered Project checkout's committed current `HEAD`. The exact source revision is durable, dirty base-checkout changes are excluded with a pre-first-message warning, and invalid restore identity fails closed without base-checkout fallback.
- **Pi internals vs Space Zero source of truth:** Pi transcripts and runtime state remain private Pi Adapter data. The SQLite-backed Session Event Journal and rebuildable projections are authoritative for Space Zero product behavior and client recovery.
- **Managed workspace content vs application data:** Space Zero Home contains user-owned managed content such as projects, worktrees, knowledge, skills, and artifacts. Private application data such as SQLite, credentials, raw transcripts, logs, and caches stays in the OS application-data directory by default. Existing projects may remain at external paths and are registered rather than moved.
- **LLM auth/models vs app state:** Pi owns LLM provider credentials and model configuration inside each Workspace Host through private Pi authentication storage; credentials are not mirrored in SQLite. Pi Adapter contains the storage format and provider behavior. Clients receive non-secret status and model information only. Future explicit credential transfer to a Remote Host requires a separate security decision.
- **Git CLI vs GitHub API:** Local repository operations should use the Git CLI. GitHub data and workflows should use Octokit.
- **Browser vs project preview:** Each Browser page is one Side Pane Tab across Project Home, Project Sessions, Global Chat, and Knowledge Base. A project preview is a normal Browser tab displaying a running project's URL, not a separate category or mode; project association may add preview/debug affordances to that tab.
- **Browser vs external browser:** The integrated Browser keeps web content and project inspection near the agent workflow; opening a URL in the user's system browser remains a distinct action.
- **Command Palette vs command behavior:** The Command Palette is a human-facing discovery and invocation surface for App Commands. It should not own the implementation of command behavior.
- **App Sidebar vs Side Pane:** The left App Sidebar owns app navigation and context selection. The right Side Pane is a substantial split-view work surface beside the context's primary workspace content and owns that context's peer tab collection.
- **Chats section vs Projects section:** The App Sidebar shows an expandable Chats section above Projects. Chats lists recent unarchived Global Chat Sessions by title only, provides an archive icon on each chat row, and provides New Chat and All Chats actions; Projects lists registered Projects and project actions.
- **Side Pane Tab vs category:** A tab is one open resource; Files, Git Diff, Browser, and Terminal are tab categories. Selecting a category from the collapsed launcher focuses its most recently focused tab or creates the category's first tab.
- **Side Pane vs category-internal state:** The Side Pane owns tab order, active tab, open/collapsed state, width, and context identity. Each category owns resource-specific state and lifecycle; Files additionally owns one shared explorer model across its tabs.
- **Side Pane context identity:** Side Pane state is independent per stable workspace context: Project Home uses its stable Project id, Project Sessions use stable Session ids, Global Chat uses one stable global chat context key for the Global Chat area, and Knowledge Base uses one stable Knowledge Base context key independent of any future Chat Context.
- **Collapsed vs expanded Side Pane:** The collapsed Side Pane shows only the vertical category launcher. Selecting a category expands the pane and focuses or creates its tab; the launcher then disappears and the Side Pane shows only its tab strip, **+** menu, and active content. Closing the final tab collapses the pane.
- **UI commands vs privileged commands:** App Commands can represent renderer-local UI/navigation actions, Desktop-native actions, or Host-owned product actions. Renderer-local actions remain local, Desktop-native actions use narrow preload/IPC APIs, and Project/Session/Git/agent actions use Client Runtime and the authenticated Host Protocol.
- **App Commands vs Workspace Tools:** App Commands are human-facing commands for the Command Palette, keyboard shortcuts, menus, and future human UI surfaces. Workspace Tools are agent-facing typed capabilities. They use separate registries, but Host-owned actions should converge on the same Workspace Host application services rather than duplicate policy in renderer or Electron main.
- **Delegation vs Workspace Tools:** Agent delegation is Pi runtime behavior contained by Pi Adapter and Workspace Host policy, not a renderer or Electron-main capability. Its concrete hierarchy and definition format remain deferred until delegation is selected for v0.1 implementation.
- **Workspace Tools vs backdoors:** Agents operate Space Zero through typed Workspace Tools that route into authorized Workspace Host application services. They do not directly mutate SQLite, bypass Host authorization/application validation, access unverified filesystem paths, or rely on renderer automation for first-class app actions.
- **UI base vs agent runtime:** The agent UI base (shadcn Chat Components + AI Elements) is presentational only: components accept plain props and emit callbacks and do not bundle an agent runtime, transport, or backend. Desktop containers feed them plain Client Runtime projections from the authenticated Host Protocol; Pi, Effect HTTP, and transport details remain outside generic UI.
- **Tool safety vs user autonomy:** Workspace Tools should declare safety levels such as read, write, and dangerous. Confirmation requirements are controlled by user settings so cautious builders can require approval while power users can allow dangerous actions without confirmation.
- **Skills vs Knowledge Base:** Skills are reusable behavioral instructions loaded on demand; the Knowledge Base stores durable user knowledge and documentation. Skills should not be silently copied into or managed as Knowledge Base content.

## Business and Product Rules

Rules for capabilities explicitly marked deferred are retained product references, not initial v0.1 implementation requirements. Active ADRs and the initial-scope rules below take precedence.

- Space Zero should optimize for reducing context switching for builders.
- Explicitly quitting Desktop stops local Project Sessions coherently and then stops the Local Host; closing the last window does not quit the app.
- Future Remote Hosts are managed by Space Zero as either on-demand or dedicated infrastructure; customer-managed self-hosting is not planned.
- Remote Access is a later feature that may connect the Companion App or another client to either a running Local Host or a Remote Host; it is not part of the initial release.
- Workspace Host authentication is mandatory even on loopback. Local startup uses a one-time protected bootstrap secret, Electron main holds Host-lifetime supervisor authority, and renderers receive only short-lived scoped client capabilities.
- Bootstrap, supervisor, and client credentials must not appear in command arguments, environment variables, URLs, logs, Session events, transcripts, workspace files, or persistent renderer storage.
- Host-owned agent Session domains are event-sourced. Project Sessions and Global Chat Sessions use the same durable event journal, projection, command idempotency, and cursor-based replay pattern; unrelated Desktop settings, credentials, filesystems, Git internals, and infrastructure configuration are not event-sourced.
- The Local Host owns one private SQLite database using Effect `4.0.0-rc.109` `@effect/sql-sqlite-node` over private Node `22.23.1`'s built-in `node:sqlite`, with foreign keys, WAL, numbered transactional migrations, versioned Session events, rebuildable projections, and command receipts.
- Effect `4.0.0-rc.109` is the exact-pinned application foundation for Host Contracts, Workspace Host, Pi Adapter, and Client Runtime. Effect HttpApi, Node HTTP Server, HTTP Client, and typed SSE implement the Host Protocol behind adapters; upgrades are deliberate and fully validated. React and generic UI components remain Effect-free.
- The repository is a pnpm workspace with separate Desktop and Workspace Host applications plus explicit Host Contracts, Client Runtime, and Pi Adapter packages. Packages never depend on applications, and applications never import another application's source.
- Desktop packages private Node.js `22.23.1` for the Local Host. Workspace Host is a hardened normal Node deployment: compiled strict ESM, pnpm-pruned production dependencies, official Node checksum verification, signed immutable resources, integrity verification, canonical launch paths, and a sanitized environment. Public builds disable Electron Node-mode and Node-options fuses and do not use `ELECTRON_RUN_AS_NODE` or `utilityProcess`.
- Pi owns Host-global LLM provider authentication in private Workspace Host application data. Secrets are not mirrored in SQLite or exposed through Session history, worktrees, logs, URLs, or persistent renderer state.
- Each Workspace Host owns its own Project catalog. Desktop keeps only disposable Project projections and never duplicates Host-owned Project persistence.
- One initial Project Session owns one Pi conversation, one Session Event Journal, one managed worktree and branch, and one focused workflow.
- A New Chat action opens a pre-send Global Chat draft UI. The Workspace Host creates a durable Global Chat Session only when the first user prompt is sent, so abandoned empty drafts do not appear in chat history. First prompt submission uses one idempotent Host command that creates the Global Chat Session, records the first user message, starts the first turn, and returns the created Session. The initial title is the trimmed first line of the first prompt with deterministic truncation to 60 characters.
- One Global Chat Session owns one Pi conversation, one durable Session Event Journal, and one durable Session-scoped agent runtime configuration, but no Project, source revision, managed worktree, branch, or Git lifecycle. It uses the same event-sourced prompt, assistant-message, turn, archive/unarchive, projection, command-idempotency, cursor-replay, runtime configuration, per-turn runtime snapshot, skills, follow-up, interrupt, retry, and recovery patterns as Project Sessions where those concepts apply. The first Global Chat implementation includes approved read-only workspace/app inspection Workspace Tools, but it must not receive Project, Files, Git, worktree-scoped capabilities, or app-state mutation tools. The initial read-only tool set is `workspace.getStatus`, `projects.listSummaries`, `globalChats.listSummaries`, and `agentRuntime.getDefaults`; more read-only inspection tools may be added as their owning features are built. `globalChats.listSummaries` returns unarchived chats by default and accepts explicit `includeArchived: true` input when archived chat summaries are needed. `projects.listSummaries` returns Project `id` and `displayName` only, with no paths. `workspace.getStatus` initially returns only host connection kind, Project count, unarchived Global Chat count, and active Global Chat/Project Session ids when available. Safe app-state mutation tools for Global Chat are a later enhancement.
- Archiving a Global Chat Session hides it from ordinary chat navigation and makes it history-only until unarchived. Archived Global Chat Sessions remain visible in the Archived tab of the all-chats screen and can be opened for history review, but cannot receive new prompts until unarchived. Opening an archived Global Chat Session shows the chat read-only with the composer disabled and an “Unarchive to continue” action.
- The App Sidebar shows up to 10 recent unarchived Global Chat Sessions by title only, sorted by last updated descending, with an archive icon on each chat row. The All Chats screen defaults to its Unarchived tab and shows each Global Chat Session title, last-message preview, and last-updated time in both Unarchived and Archived tabs. Unarchived chats sort by last updated descending; archived chats sort by archived time descending. The first implementation does not include chat search/filter. When no Global Chat Session is selected, the Chat area opens the All Chats screen; if there are no chats to show, it displays an empty placeholder with a CTA to create a new chat. The All Chats screen also provides a New Chat action outside the empty state. App restart should restore the last active Global Chat route when that route was active before quit; if the selected Session is unavailable, Space Zero falls back to All Chats. Users can rename Global Chat Sessions from the active chat header, including while an archived chat is open read-only. Archive/unarchive actions are available from the All Chats screen and the active chat header; unarchived chats can also be archived from their App Sidebar row. Archiving the active Global Chat Session keeps the chat open, switches it to the read-only archived state, and removes it from the App Sidebar recent chat list. Unarchiving from the active chat header keeps the same chat open, re-enables the composer, and returns it to the recent chat list according to last-updated order.
- Project Sessions require a Git repository with a valid current `HEAD`; non-Git folders are deferred.
- Session creation branches from the registered checkout's committed current `HEAD`. Dirty changes are excluded and disclosed above Chat input until the first message is submitted.
- Local worktrees live under `<Space Zero Home>/worktrees/<project-id>/<session-id>` and never inside registered repositories.
- Session provisioning is a durable lifecycle. Pi starts only after worktree creation and identity validation; restart recovery reconciles incomplete provisioning explicitly.
- Desktop automatically restarts an unexpectedly crashed Local Host with bounded backoff while the app is running, using a fresh bootstrap and fresh capabilities. It never automatically replays work that may already have produced external side effects.
- Testing follows runtime ownership: real headless Host integration covers HTTP/SSE, SQLite, Git, and recovery; broad Electron UI/navigation/screenshot E2E uses a deterministic contract-compatible mock Host; a narrow real-Host Electron suite and packaged smoke tests verify process, security, native-runtime, and shutdown boundaries.
- Desktop quit retains managed worktrees for restoration. Archive removes the verified worktree/branch but retains history; deletion cleans resources before removing history. Failures never claim successful cleanup.
- Remote Projects run both the agent and workspace on the Remote Host; local agent execution over SSH/SFTP-mounted remote files is not supported.
- Future Session Handoff is local-to-remote only, starts from an idle Session, and uses an explicit checkpoint whose format remains undecided.
- v0 public builds are downloadable from the Commercial Website and hosted through GitHub Releases, but installed app usage is gated by Convex-backed Space Zero Account sign-in and License Activation.
- The monorepo has separate `apps/website` and `apps/account` applications: Website uses Astro and owns commercial/landing/download pages, while Account uses Next.js 16 and owns Convex-backed sign-in, checkout, entitlement, communication consent, and desktop activation backend behavior.

- The website signup/purchase flow may offer GitHub OAuth as a Space Zero Account identity method only; GitHub repository access is granted later inside the desktop app.

- The App Sidebar account affordance stays compact: it shows the signed-in account's email or GitHub username, plus avatar when available. Detailed account management lives in Settings rather than the sidebar.
- Desktop Settings includes an Account page that shows account identity, current plan/entitlement state, and a GitHub App access row for repository authorization status and management.
- The GitHub App access row should preserve the existing v0 repository-management capability: connect through the GitHub App/device flow, open GitHub App installation management for selected repositories, recheck live installation/repository access, show accessible repository status, and keep **Repository access required** when no usable installation repository is found. It must not infer a fake pending-organization-approval state.
- Beta users may receive free or fully discounted Polar-backed entitlements; those entitlements may later be deactivated or migrated into discounted renewal offers.

- The commercial website should point macOS users to a signed/notarized DMG download, while the release may also publish ZIP/update metadata artifacts needed by the auto-updater.

- The app should favor a clean desktop GUI over terminal-first workflows.
- The v0 agent strategy is Pi-first; do not add multi-harness abstractions without a new decision.

- GitHub should be integrated deeply, not treated as a link-out-only experience.
- New projects and repositories created or cloned by Space Zero use `Space Zero Home/projects` by default. Existing repositories may remain at external paths and are registered without being moved. The Knowledge Base remains separate under `Space Zero Home/knowledge-base`.
- Knowledge Base image uploads use the fixed Knowledge Base-relative `assets/img/` directory and relative Markdown links; there is no attachment-location setting.
- Files is a lightweight manual editing surface rather than a complete VS Code/Cursor workbench. Diffs Edit from `@pierre/diffs` is its source editor, and Trees (`@pierre/trees`) is its renderer-only file explorer interaction and model foundation. Space Zero owns Side Pane tabs, context isolation, dirty/save behavior, restoration, filesystem integration, and the privileged file-management services behind the explorer.
- The Files tree uses Trees' icon system with the broad built-in icon set and targeted Space Zero remaps only where product recognition requires them. Files uses Trees' compact density, enables sticky folders, derives Trees styling from Space Zero/editor theme variables where possible, and always compacts single-child directory chains using Trees' compact-folder behavior, so a path like `src/features/files/renderer` may appear as one navigable chain instead of several low-value intermediate rows. Within a directory, folders sort before files using natural case-insensitive ordering. v0 has one selected tree item at a time; multi-selection is deferred with bulk operations. The tree shows hidden and Git-ignored content but always hides and protects `.git` internals. For large trees, Files follows Trees' prepared-input guidance: the owning Workspace Host loads canonical paths, applies Space Zero exclusions and ordering, and passes prepared or presorted input through Client Runtime rather than doing expensive tree shaping in UI code. Symbolic links appear as identifiable entries but v0 does not follow, expand, edit through, search through, rename, move, or trash them; Files exposes metadata and a reveal-in-system-file-manager action instead.
- Every Files tab renders the same context-scoped explorer model beside one file editor. Explorer expansion, search, width, collapsed state, scroll, and selection are shared across Files tabs; activating a Files tab selects and reveals its file. The explorer search has two modes: **Files search** filters the Trees explorer by canonical path/name, while **Contents search** uses the owning Workspace Host's rooted search capability and replaces the tree with file/line/context results.
- Opening Files with available files but no Files tab creates an empty Files tab with the explorer expanded and waits for a selection. An empty root starts with the explorer collapsed and a **Create new file** CTA; a created file opens immediately as a permanent Files tab.
- Files uses at most one clean preview tab per context. A single-click tree selection opens or replaces that preview. Double-clicking, editing, saving, or explicitly pinning makes it permanent; after pinning, the next single-click creates a new preview. Dirty tabs are permanent and never replaced. Selecting a file already open permanently focuses its existing tab. Files tabs live directly in the Side Pane tab strip and may be reordered; there is no nested Files tab strip.
- Files treats any valid UTF-8 content without binary markers as editable text regardless of filename extension. Diffs provides syntax support for recognized filenames and languages and plain-text editing otherwise. Saving preserves an existing UTF-8 BOM and LF/CRLF line-ending convention rather than normalizing them silently; newly created files use UTF-8 without BOM and LF.
- Files limits Diffs and rich Markdown editing to text files no larger than 2 MiB in v0. Larger files open as non-editable metadata views with an action to reveal them in the system file manager; the limit may become configurable later.
- Files previews PNG, JPEG, GIF, and WebP images up to the existing 10 MiB image limit. SVG remains editable text in Diffs rather than rendered as trusted image content. Other binary files and oversized images open as non-editable metadata views with a reveal-in-system-file-manager action.
- Files uses explicit save for every editable file. `mod+s` saves the active file, while **Save All** saves every dirty Files document in the current context; saving a preview pins it. Save All reports failures per file and leaves failed documents dirty. Save As is out of scope for v0. Files does not use timer-based or background autosave, and changing Side Pane tabs, categories, or contexts does not implicitly save. Dirty buffers remain in memory across those changes. Closing a dirty tab requires Save, Discard, or Cancel; clean tabs close immediately, and save failures keep the dirty tab open with an actionable error.
- Markdown and MDX Files tabs open in **Source** mode using Diffs. The same tab may switch to the existing **Rich** Markdown editor. Switching Source↔Rich saves first; save failure or an external-change conflict blocks the switch. Rich mode is remembered only while that tab remains open during the current app run, and restored Markdown tabs start in Source. The editors keep separate undo histories and the destination starts from the saved baseline.
- Files restores saved working state independently per context after app restart: permanent file tab paths and order, active permanent tab, Diffs cursor/selection/scroll view state, and expanded tree folders. Preview tabs and Rich mode remain memory-only and are not restored. v0 does not persist unsaved buffer content as recovery drafts. Normal quit or restart with dirty documents requires Save All, Discard All, or Cancel; a crash or forced termination may lose unsaved edits. Hot-exit draft recovery is a later enhancement.
- Files provides two search modes within the active context root. **Files search** is the default explorer search mode and uses Trees' `hide-non-matches` mode to filter visible rows by canonical path/name. **Contents search** is explicit, routes through the owning Workspace Host's rooted search capability, respects `.gitignore` and common generated-directory exclusions by default, supports an **Include ignored files** option, always excludes `.git`, skips binary and files over 2 MiB, and opens results as preview tabs. Initial search is on demand without a persistent index.
- Files is a filesystem surface and shows read-only Git status decorations in both Project Session and Knowledge Base explorers through Trees' Git-like row signals. Files may also use Trees row annotations for critical filesystem policy markers that affect user action, such as symlink, protected/locked, or open-tab conflict states. Saving or mutating files only changes the active working tree; Files never stages, unstages, reverts, commits, checks out, or invokes other Git behavior. Git owns diff review, staging, recovery, commit, and branch workflows, and observes filesystem changes independently.
- Workspace Host-owned file watching and optimistic revisions detect external file modifications. A clean open tab reloads automatically; a dirty tab preserves its local buffer, enters a conflict state, and must choose **Reload from disk** or explicitly confirmed **Overwrite disk** before saving. v0 does not automatically merge external and local edits, and neither version is overwritten silently. If an open file disappears, its buffer remains open in a **Deleted on disk** state with explicitly confirmed **Recreate file** or **Close tab** actions. v0 treats external renames as deletion plus creation rather than guessing path identity, and refreshes the tree to show the new path.
- Project Session and Knowledge Base Files expose the same rooted file operations: create a file or folder, inline rename through Trees, move by Trees drag-and-drop or validated relative destination path, context-menu actions opened by right-click or a subtle row hover trigger button, move to the operating system Trash with confirmation, and reveal in the system file manager. Trees drag/drop is disabled while Files search is active. Files does not provide an Open in external editor action or preferred-editor setting. Trash failure never falls back silently to permanent deletion; an explicit permanent-delete action is a later enhancement. Rename, move, or trash affecting dirty tabs requires Save, Discard, or Cancel first. Successful rename or move rewrites affected open-tab paths and keeps them open; trash closes affected tabs only after the operation succeeds. These operations share a capability contract but always validate against the active context root in the owning Workspace Host. Copy/paste, duplication, bulk operations, and arbitrary file import are later enhancements.
- New Project Sessions and Global Chat Sessions should start from the same Host-global default model and default thinking level configured through Space Zero Settings and owned by the Workspace Host. These defaults are durable Host state stored outside the Session Event Journal; they seed Session creation but are not themselves Session facts. A fresh Host starts with no selected default model or standalone default thinking level; default thinking is defined only for the selected default model. After the first successful subscription or API-key authentication, if no default is set and the newly authenticated provider has available models, the Host auto-selects the first available model from that provider using the Host/Pi catalog ordering and sets the default thinking level to the first supported thinking level reported for that model. Default thinking choices are constrained to the selected model's supported thinking levels. If the selected default model changes and the previously selected thinking level is unavailable for the new model, the Host switches default thinking to the first supported thinking level for the new model using the Host/Pi catalog ordering. Once a Host-global default model exists, adding or changing provider authentication must not overwrite it automatically. If the selected default model becomes unavailable because its provider authentication is removed, the Host clears it and may auto-select another available model so new Session creation keeps working. Each durable Session may override both independently. Per-project default model/thinking is a v1 enhancement with project settings, not v0.
- LLM provider credentials and model configuration are owned by Pi inside each Workspace Host and are not mirrored in SQLite. Renderer Settings/Model UI uses authenticated Host commands and receives only non-secret status/model information. Desktop may open the OS browser and handle a `spacezero://` OAuth callback, but durable credential ownership remains in Host-side Pi authentication storage.
- Skills use `<Space Zero Home>/skills` as the native global location and also support `~/.agents/skills`, project `.agents/skills`, and project `.pi/skills`. Project skills take precedence over global skills after a persisted project-trust decision; without one, project-local skill discovery fails closed. The chat composer exposes available skills through `/skill:name` discovery while Pi owns command expansion. Settings provides global-skill enable/disable controls for the Space Zero Home and `~/.agents/skills` locations; disabled global skills are excluded from new or reloaded agent sessions, while project-local skills remain project-scoped.
- A future conversation-rotation slice may list skills and chat commands in one composer suggestion area. `/clear`, `/resume`, and Chat Context history remain deferred and require a new Session/conversation decision before implementation.
- Meaningful user actions should be implemented as application capabilities that can be reached by the renderer UI and, when appropriate, exposed as Workspace Tools for agents.
- Side Pane open/collapsed state, width, tab order, active tab, and category-specific restoration metadata persist independently for each workspace context. Browser pages restore lazily at their saved URLs, Terminal tabs restart fresh shells at their last validated working directories, Git Diff queries fresh repository state, and Files restores permanent file references and view state.
- A context with no saved Side Pane tabs starts collapsed with the category launcher visible, except Knowledge Base creates and shows an initial empty Files tab so the builder immediately sees its explorer. Saved context state takes precedence afterwards.
- The Side Pane is sized as a substantial split view rather than a narrow sidebar. Its initial width is approximately 60% of the workspace area beside the App Sidebar, it remains resizable, it should have roughly a 400px minimum, and it must preserve roughly 360px for chat instead of using a fixed maximum width.
- The Side Pane shell uses the same background color as the primary chat surface. Category-specific internal chrome and styling belong to each category's product contract.
- The initial Side Pane supports collapsed and resizable split-view states only. Maximizing over chat, detached panes, and additional editor windows are later enhancements.
- Filesystem-backed Side Pane categories receive context-specific initial roots. Project Home Files and Git Diff are rooted in the registered Project checkout, while Terminal starts there. Project Session Files and Git Diff are rooted in the Session's managed worktree, while Terminal starts there. Knowledge Base Files and Git Diff are rooted in the Knowledge Base repository, while Terminal starts there. Global Chat Terminal starts in Space Zero Home. Browser has no filesystem root.
- The Terminal behavior below is retained future product reference, not an initial v0.1 implementation contract. Terminal transport, persistence, reconnect, lifecycle, and remote behavior require an active ADR before implementation. A Terminal's context root is intended as a validated starting directory and restoration fallback, not a filesystem sandbox. Shells run with the builder's normal operating-system permissions and may navigate anywhere those permissions allow without changing the owning Project Session, Global Chat, or Knowledge Base context. Files and Git remain confined to their separate context capability contracts.
- Each workspace context owns isolated Terminal Side Pane Tabs. Creating a Terminal tab launches one terminal at the context's fixed initial root; tabs never move between or inherit state from Project Home, another Project Session, Global Chat, or Knowledge Base.
- A Terminal tab's visible label is the basename of its last validated working directory and updates when shell integration reports a directory change; it falls back to the shell name when no directory label is available. v0 does not accept shell-controlled window-title sequences or provide manual tab renaming.
- A future Terminal tab is intended to launch the builder's configured operating-system shell on its owning Workspace Host. Space Zero does not provide custom shell profiles or per-tab shell selection. macOS and Linux use the user's configured shell, Windows uses PowerShell, and launch failures are reported with actionable guidance rather than silently choosing a different shell.
- Future Terminal shells run as normal interactive shells on the owning Workspace Host with that Host's sanitized inherited environment and the user's standard shell startup behavior. Space Zero sets only terminal essentials such as terminal/color capability, the validated starting directory, and lightweight shell integration needed to report working-directory changes; it does not parse shell startup files, load project `.env` files, or inject project-specific secrets or variables. User-configured environment managers remain shell-owned.
- Each future Terminal Side Pane Tab owns exactly one Host-side PTY and remains bound to its owning workspace context. Its process may continue while a client switches tabs or disconnects according to a later Terminal lifecycle decision. PTY shutdown on tab close, context deletion, Host shutdown, and remote disconnect must be specified before Terminal implementation.
- The retained local Terminal design does not replay previous commands after Host or app restart; exact restoration and reconnect behavior remains subject to the required Terminal ADR. On restart, every previously open tab is restored in its prior order as a fresh shell at that tab's last validated working directory, with the same active-tab selection and empty terminal output. Space Zero uses lightweight shell integration to receive current-working-directory updates rather than attempting to infer `cd` commands from terminal text. If integration is unsupported or a saved directory is missing or no longer valid as a launch directory, the tab falls back to that context's fixed initial root and reports the fallback.
- In the retained Terminal UX, **Close Tab** is the primary terminal-termination action: closing a live Terminal tab requires confirmation, terminates its PTY/process tree, and removes the tab and its in-memory output. There is no separate Stop or Kill Terminal action. `Ctrl+C` remains ordinary terminal input. When a shell exits naturally, including through `exit` or `Ctrl+D`, Space Zero closes its Side Pane Tab automatically; closing the final Side Pane Tab collapses the pane. App quit and context deletion use one aggregate confirmation for affected live terminals rather than prompting once per tab. A global preference may disable these confirmations for builders who prioritize speed.
- The retained Terminal UX bounds each tab's in-memory scrollback by 10,000 lines or 5 MiB, whichever comes first. The owning Workspace Host retains bounded output while clients are detached and replays it through the future authenticated terminal protocol, so Terminal does not depend on mounted renderer components. Reaching either limit discards the oldest output without stopping or throttling the PTY. Terminal output should remain memory-only unless the required Terminal ADR explicitly selects a secure persistence policy.
- The retained Terminal UX does not define a tab/PTY cap yet; builders are responsible for the processes they start. Output buffering remains bounded independently so runaway output cannot consume unbounded application memory.
- Terminal privilege belongs to the Workspace Host that owns the workspace, not the renderer or Electron main. A future client receives opaque terminal IDs and only typed create, subscribe, unsubscribe, input, resize, and close capabilities through an authenticated terminal protocol. The Host validates Session/context ownership, starting/restored directory, capability scope, and operation input. Embedded Browser content receives no Terminal access.
- The future authenticated Terminal protocol does not filter or approve commands entered by the builder. Once Workspace Host creates the authorized PTY, terminal input passes through unchanged and the shell may perform anything allowed by the Host account. The boundary prevents clients from choosing an untracked executable, startup environment, or initial path; it does not turn the shell into a restricted command environment.
- Whether Workspace Host persists Terminal tab metadata, and which metadata is client-local instead, remains part of the required Terminal ADR. Live PTYs, terminal output, command history, and environment contents must not be persisted without an explicit privacy and recovery decision.
- Switching away from a Terminal Side Pane Tab preserves its running PTY, in-memory viewport, and scroll position without changing cwd or creating tabs. Switching contexts shows only the destination context's isolated tab collection. Restoring navigation does not move keyboard focus into Terminal unless the builder explicitly selects it.
- Only the visible active Terminal tab is fitted and resized to the current Side Pane dimensions. Hidden Terminal tabs retain their last PTY dimensions until shown again. The renderer computes columns and rows with `@xterm/addon-fit` and sends bounded dimensions through the future authenticated terminal protocol; Workspace Host validates them before resizing the PTY.
- The retained Terminal UX recognizes web URLs in terminal output and require `mod+click`; ordinary clicks continue normal terminal selection behavior. A Terminal Link is navigation, not command execution: arbitrary output is never made click-to-run.
- Activating a Terminal Link creates and focuses a Browser Side Pane Tab in the same workspace context without stopping the terminal. Returning to the Terminal tab restores its scroll position. If Browser is unavailable, Space Zero explicitly offers to copy the URL or open it in the operating-system browser; it never opens external content silently.
- The shared Git Diff tab is a diff-first, AI-assisted review surface in Project Sessions and the Knowledge Base. Background activity may refresh Git state, but must not stage files, create commits, pull or rebase, or push. The legacy Knowledge Base automatic sync behavior is replaced rather than carried into the shared surface.
- Git Diff stacks file diffs with per-file headers rather than presenting only a compact status list. Text-file diffs are expanded by default, independently collapsible, and fold unchanged regions; binary or excessively large changes show a bounded summary instead of rendering excessive content. A changes selector defaults to **Uncommitted**. Eligible text diffs are editable in **Uncommitted** and **Unstaged**, changing the shared unsaved working document buffer; **Staged** remains read-only because it represents index content. Git Diff still has no file-selection checkboxes or direct stage, unstage, discard, commit, pull, rebase, or push mutations.
- In Project Sessions and Knowledge Base, Git Diff includes a commit composer that routes the builder's commit instructions to the active agent Session rather than executing Git from renderer UI. Project Home has no active chat Session, so its Git Diff tab omits agent actions and remains a manual review/edit surface. Submitting the composer immediately sends a normal prompt through the Session's standard agent prompt path without reading, replacing, or appending to the primary chat draft; the request and response remain visible in the Session transcript. Composer text is optional: an empty composer asks the agent to choose an appropriate commit message, while entered text supplies the builder's preferred message or instructions. **Commit** is available when uncommitted changes exist; **Commit & Push** and **Commit and create a PR** are available when changes exist or the branch is ahead of its upstream, even when no remote is configured. In that case the agent may commit locally, explain why it cannot push, and ask the builder for the missing remote information in chat. **Commit and create a PR** reuses the commit-and-push flow, then uses authenticated GitHub tooling available to the Session, deterministically reuses an existing open pull request for the head branch when possible, and otherwise creates a non-draft pull request. Its final response includes the usable pull request URL; if the push succeeded but pull request creation failed, the agent reports that partial success and the actionable creation failure without claiming completion. During conflicts all three actions are replaced by **Resolve with agent**. Each shortcut asks the agent to inspect fresh repository state and handle the full workflow; the rendered diff is not copied into the prompt. A workspace-global Git setting chooses **Commit**, **Commit & Push**, or **Commit and create a PR** as the composer's visible primary action, defaulting to **Commit & Push**, while a small action menu offers the other choices for one request without changing the saved preference. The agent performs and explains staging, commit, remote, divergence, conflict, and pull request workflows through its existing project capabilities and authenticated tooling; Space Zero's future GitHub credential remains outside renderer and project command environments; its Host-access boundary requires a separate active decision before GitHub workflow implementation. Git-originated prompts add no separate prohibition on discard, reset, or other Git operations; the agent follows the builder's instructions and the existing agent tool safety and confirmation policy. Git agent actions are disabled while the active agent is running; they do not interrupt the run or create a hidden prompt queue.
- When a repository has unresolved conflicts, Git Diff shows a prominent conflict state and places conflicted files before other diffs. Dedicated conflict editing remains outside Git Diff; **Resolve with agent** immediately sends a normal, transcript-visible conflict-resolution prompt to the active agent without changing the primary chat draft.
- Git Diff shows a compact current-branch label and upstream divergence such as ahead/behind counts, without remote-management controls.
- Git Diff refreshes when it becomes visible, while visible when repository changes are detected, when Space Zero regains focus, and when a Git-originated agent run finishes; it also provides manual **Refresh**. Refresh re-queries repository state rather than tracking a separate commit workflow and preserves the current changes filter, expanded-file state, and scroll position where the changed diff still permits it.
- Git Diff restoration queries fresh repository state and returns review controls to their defaults; filters, expanded files, scroll position, and unsent commit-composer text are session-only even though the singleton Side Pane Tab itself is restored.
- Files and Git Diff share one Space Zero-owned dirty document buffer. Editing an eligible diff never auto-saves or creates a Files tab. Diffs-based Files and Git Diff surfaces share compatible document undo history but retain independent cursor, selection, and scroll state. Activating a filename or line focuses its existing Files tab or opens a permanent one near that line.
- Markdown and MDX diff editing is disabled while the corresponding Files tab is in Rich mode; Git Diff stays readable and the builder must save and switch the Files tab to Source before editing the diff. A dirty document edited only through Git Diff remains visible in a pending-edits section when filters, refresh, or repository state would otherwise remove it.
- Closing Git Diff prompts only for dirty documents that would lose their final editor surface, with **Save and close**, **Discard and close**, and **Cancel**. Save/discard applies to all such documents; save failures or conflicts keep Git Diff open, leave failed documents dirty, and report per-file errors. Dirty documents still open in Files remain visible and do not require that prompt.
- Git Diff renderer requests identify the active trusted context, never an arbitrary repository path. The owning Workspace Host resolves and validates a Project checkout, Project Session managed worktree, or future Knowledge Base repository, runs local Git queries, and returns typed status/diff data through Client Runtime and the authenticated Host Protocol.
- A future Knowledge Base Chat may receive narrowly scoped Knowledge Base Git Workspace Tools backed by Workspace Host services so its agent can inspect state and fulfill approved Git workflows under Host authorization and tool safety policy. This does not make Git available to Global Chat. Project Session agents continue operating on their authenticated managed worktree through Pi project tools.
- Project Home, Project Sessions, and Knowledge Base expose Files, Git Diff, Browser, and Terminal Side Pane categories. Global Chat exposes Browser and Terminal. The collapsed launcher shows the categories available in the current context; the expanded Side Pane shows only tabs and the **+** creation menu.
- Every Browser page is one Side Pane Tab. General web pages and Project Session previews coexist as normal peer tabs and receive no automatic Preview badge or localhost classification. Tabs use page title and favicon, falling back to hostname or URL. Project Home, each Project Session, Global Chat, and Knowledge Base own isolated collections that must not leak into another context. Creating Browser opens a blank tab with its URL field focused. Closing the final Side Pane Tab collapses the pane. Browser tabs may be dragged to reorder with other Side Pane tabs, and their order is restored; pinned tabs, tab groups, and tab duplication are out of scope for v0.
- Browser preserves each Side Pane Tab's last committed URL across app restarts. Full back/forward history is preserved only while the app is running; restored tabs start a fresh history stack at their saved URL. During an app run, tabs remain live while inactive, the Side Pane is collapsed, or the builder switches contexts, preserving page, form, media, and navigation state. Closing a Browser tab disposes that tab's live web content; permanently deleting its owning Session or Knowledge Base context removes all Browser state and live resources for that context. Ordinary navigation or archiving does not remove Browser state.
- After app restart, Browser restores tab metadata lazily. The active tab loads when its Browser context is first shown, and other tabs load when selected. A failed or unavailable URL remains in its tab with an error and retry action rather than being removed.
- Browser does not discover or scan for project dev servers. Builders open preview URLs manually or through explicit URL links and handoffs exposed by Space Zero.
- Chat links follow the workspace-global **Open chat links in** setting, which defaults to **Space Zero Browser** and also offers **Default browser**. Space Zero Browser opens the link in a new tab belonging to the same Project Session, Global Chat, or Knowledge Base context as the chat.
- Terminal URLs support an explicit `mod+click` handoff to a new tab in the Space Zero Browser belonging to the same context. This handoff always targets Space Zero Browser and does not use the chat-link opening preference.
- Browser v0 navigation chrome provides back, forward, reload/stop, an editable URL field, new tab, close tab, and **Open in default browser**. Reload becomes Stop while navigation is in progress. The URL field navigates recognizable URLs and localhost addresses directly and sends other text to Google Search. Home, bookmarks, and a downloads manager are not part of v0.
- Browser v0 provides standard focus-scoped shortcuts for focusing the URL field (`mod+l`), creating a Browser Side Pane Tab (`mod+t`), closing the active tab (`mod+w`), reloading (`mod+r`), and platform-native back/forward navigation. They apply only when Browser is the active focused tab, resolve through stable command identities, and participate in the existing user-remappable shortcut system.
- Web content may not create uncontrolled Electron windows. An `http` or `https` link that requests a new window opens as a new Space Zero Browser tab in the same context. A supported non-web protocol such as `mailto:` is handed to the operating system only after user confirmation; malformed and unsupported protocols are denied.
- Every Browser download requires a native **Save As** choice. Dismissing the dialog cancels the download. Completion is reported through a lightweight notification with **Open** and **Reveal in folder** actions; v0 does not provide silent downloads or a persistent downloads manager.
- Sensitive web permissions are denied unless the builder approves an origin-specific prompt. v0 offers **Allow for this app run** or **Deny**; grants are not restored after restart. Camera, microphone, location, notifications, clipboard access, MIDI, and similar capabilities are never granted silently, and Chromium sandbox restrictions still apply.
- Certificate errors may be bypassed only for loopback URLs (`localhost`, `127.0.0.1`, and `[::1]`) after a clear **Proceed for this app run** warning. Browser never offers an invalid-certificate bypass for remote hosts.
- All Space Zero Browser tabs share one dedicated persistent browser profile across workspace contexts. Its cookies, site storage, and authenticated sessions survive app restarts until the builder clears them. The profile is isolated from both the privileged Space Zero app renderer and the user's system-browser profile; temporary permission grants are not part of its restored state.
- Settings provides a confirmed **Clear Browser Data** action for the shared Browser profile's cookies, site storage, and cache. Clearing data applies across all contexts, retains saved tab URLs, and reloads live tabs into clean signed-out site sessions. Browser v0 does not store passwords or synchronize browser profiles.
- Every loaded page, including localhost project previews, remains sandboxed and receives no Node.js access or Space Zero preload API. Browser content cannot directly access the privileged app renderer. Any future inspection or debugging capability must use controlled Electron/Chromium facilities owned behind the main-process boundary rather than weakening page isolation. User-facing Developer Tools and integrated debugging UI are out of scope for Browser v0.
- Browser blocks script-created popups that are not caused by a user gesture. Ordinary user-initiated new-window links open as tabs, but authentication flows that require `window.opener` may use controlled temporary Browser child windows. Child windows share the dedicated Browser profile, retain the same sandbox, and close when the flow completes, the parent tab closes, or the app exits.
- Browser v0 is builder-operated. Agents cannot navigate tabs, inspect or interact with pages, or receive page content implicitly. Future agent-facing Browser Workspace Tools may build on approved main-process capabilities but require separate product and safety decisions.
- The collapsed Side Pane launcher shows the categories available in its active context. Registered but unavailable categories may remain visible as disabled, keyboard-inert controls labeled “Coming soon”; they cannot create or restore tabs. If a context has no available categories or tabs, the Side Pane remains collapsed.
- Side Pane category identities are stable and shared across contexts: `files`, `git`, `browser`, and `terminal`. Contexts configure which categories are available and how they operate; adding a future category should extend the registry/configuration rather than require a new Side Pane implementation.
- The Side Pane owns context identity, available categories, tab order, active tab, open/collapsed state, and width. Each category owns its resource state and lifecycle; switching tabs must not implicitly reset the previous tab, and the pane must not depend on keeping inactive renderer components mounted. Category-specific restart restoration belongs to each category contract.
- The Command Palette should be a searchable mini Raycast-like UI inside Space Zero over the App Command Registry, not a place where command behavior is implemented directly.
- App commands should have stable IDs, user-facing titles, categories, optional search keywords, optional default keyboard shortcuts, and handlers or invocation targets.
- App commands may include renderer-local UI commands, Desktop-native commands, and Host-owned product commands. Renderer-local actions remain in renderer code, Desktop-native actions use `window.spacezero` and typed preload/IPC, and Host-owned actions use Client Runtime and the authenticated Host Protocol.
- The Command Palette itself is renderer-owned UI. It owns presentation, search, keyboard interaction, and selection state, not privileged app behavior.
- The v0 App Command Registry should be generic to the app and does not need context-aware command availability. Context-aware commands, such as commands depending on the current project, session, selection, or focused panel, are a later enhancement.
- Workspace Tools should be designed as reusable internal application capabilities, but v0 exposes them only to the in-app Agent Workspace. External automation surfaces such as a CLI, MCP server, local socket, or public API are future possibilities, not v0 commitments.
- The initial rebuild has two user-facing Session kinds: **Project Session** and **Global Chat Session**. A Project Session is triggered from a Git Project and owns one Pi conversation, one Session Event Journal, and one dedicated managed worktree/branch. A Global Chat Session is created from the Global Chat surface on first prompt and owns one Pi conversation and one Session Event Journal without a Project/worktree/Git identity. Knowledge Base Chat and rotatable Chat Contexts remain deferred capabilities retained only as product references until explicitly reintroduced.
- Knowledge Base Chat, its stable workspace context, `/clear`/`/resume`, and Chat Context history are deferred product references for v0.1. Their persistence, Host ownership, and recovery behavior require an explicit reintroduction decision.
- Future Knowledge Base setup and repository recovery may use temporary full-page states rather than chat contexts, but this is not an initial implementation requirement.
- Workspace Tools should be grouped by product domain, matching feature areas such as workspace, projects, sessions, settings, and preview. Composed tools such as `workspace.getStatus` are allowed when they serve a clear product need, but teams should not create aggregate tools speculatively for every feature.
- Space Zero should keep a lightweight Agent Activity History for agent Workspace Tool calls. It should capture enough to explain what happened without becoming a heavy compliance audit system or storing sensitive full payloads by default.
- Keyboard shortcuts should be app-focused command accelerators in v0. They work when Space Zero is focused and should not use OS-global Electron `globalShortcut` registration for normal app actions.
- The Side Pane foundation provides a **Toggle Side Pane** App Command using `mod+shift+b` and makes the collapsed category launcher and expanded tab strip keyboard accessible. Category creation and focus commands invoke the shared Side Pane controller rather than creating separate pane behavior.
- Keyboard shortcuts should resolve to stable App Command IDs rather than directly calling scattered callbacks. This follows editor-style command systems, where shortcuts, command palette entries, menus, and buttons can converge on the same command handler.
- Keyboard shortcuts should be user-remappable like VS Code/editor keybindings. The foundation should separate command identity, default keybinding, and user override keybinding.
- Keyboard shortcuts should support context-aware activation, similar to editor `when` clauses. The v0 implementation can start with simple context flags such as text input focused, modal open, command palette open, terminal focused, preview focused, or editor focused.
- Keyboard shortcuts should use a normalized cross-platform syntax such as `mod+k`, `mod+shift+p`, `alt+enter`, and `escape`. `mod` maps to Command on macOS and Control on Windows/Linux, while UI can render platform-native labels.
- Keyboard shortcut v0 should support single-stroke shortcuts only. Multi-step key chords such as `mod+k mod+s` are a future possibility, not part of the initial foundation.
- Keyboard shortcut event handling and shortcut resolution live in the renderer because shortcuts are in-app UI behavior. A shortcut handler uses the normal owning boundary: preload/IPC for Desktop-native behavior and Client Runtime/Host Protocol for Host-owned product behavior.
- An Agent Definition may be selected as a session persona only while a session is fresh (before its first prompt); the selection locks once the session starts, but the session may still override model and thinking level afterwards. When a definition is selected, its model and thinking level override the workspace-global defaults.
- Agent Definition discovery is lenient and diagnostic-driven: invalid global files are skipped with reasons surfaced in Settings, while project-file diagnostics belong to a trusted Project Session context; shadowed files are shown with their precedence status in the applicable catalog. Using a definition is loud: unknown models, empty tool allowlists, or reserved not-yet-supported fields (`output`, `blocking`) fail with explicit errors and never silently reinterpret the file's intent.
- Workspace Tool results should be structured data only. Agents are responsible for interpreting and summarizing tool results in conversation; tool results should not include polished human-readable summaries.
- Workspace Tools should be exposed through an explicit Workspace Tool Registry rather than ad hoc callable functions. The registry is the approved catalog passed to the agent harness, including tool names, input schemas, safety levels, and handlers.
- Each Host feature owns Workspace Tool definitions near its Workspace Host application services. Workspace Host composes approved feature tools and exposes them to Pi through Pi Adapter.
- Host Protocol handlers, App Command targets, and Workspace Tool handlers may be separate entrypoints, but Host-owned behavior routes into the same Workspace Host application services for the underlying use cases. Desktop-native behavior remains a separate Electron-main boundary.
- The App Command Registry and Workspace Tool Registry are separate catalogs because human-facing commands and agent-facing tools need different metadata, schemas, safety policy, and UX. They may converge on the same application services when they affect app state.
- Workspace Tools may include both domain/application actions and UI/navigation control actions. Tool metadata should distinguish UI control tools from app-state tools so safety policy, history, and agent instructions can treat them differently.
- Any future UI-control Workspace Tool still enters through Workspace Host authorization and safety policy. It may publish a typed client-facing intent only through the Host Protocol; clients decide how to present supported intents. Agents never manipulate renderer internals directly.
