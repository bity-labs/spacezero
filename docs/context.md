# Space Zero Project Context

## Purpose

Space Zero is an agentic desktop workspace for software builders.

The product exists to help builders plan, code, debug, manage knowledge, and ship software from one clean desktop GUI with minimal context switching.

## Product Thesis

Current AI building workflows are fragmented across AI chats, IDEs, terminals, browsers, docs, issue trackers, logs, and deployment tools. Space Zero should keep the builder's full working context in one place: code, agents, live sessions, skills, running app previews, debugging information, voice input, GitHub state, and project knowledge.

Space Zero owns the **builder-workspace layer**, not the agent-routing layer. The workspace, memory, and task-to-ship loop are the product. The agent harness is an implementation detail.

## Primary User

The primary user is a software builder who uses AI agents while building applications. They need to supervise agent work, inspect running apps, edit code, review diffs, manage GitHub work, and retain project context without constantly switching tools.

## Product Shape

- A real desktop GUI, not a terminal-first or TUI-first app.
- A polished project/session workspace inspired by tools like Conductor, Devin, VS Code, and Zed.
- Project sessions are first-class, with live sessions visible in a dedicated app surface.
- Editing, navigation, diffs, terminal/session output, browser preview, and debugging should converge in the desktop app.
- Pi is the default agent harness for v0.
- GitHub integration is first-class: issues, sessions, branches/worktrees, commits, PRs, reviews, and statuses should connect into one workflow.

## Important Distinctions

- **Renderer vs main process:** Renderer code is UI. Main process code owns native desktop capabilities, SQLite, Git/GitHub system work, and future agent process orchestration.
- **Terminal emulator vs terminal process:** `@xterm/xterm` and `@xterm/addon-fit` provide terminal display, input, and responsive sizing in the renderer; they do not create a shell. Electron main owns PTY-backed shell processes through `node-pty`, and preload exposes only narrow typed Terminal operations and events through `window.spacezero`.
- **Agent harness vs product layer:** Pi powers agent execution, but users should experience Space Zero as a workspace, not as a thin CLI wrapper.
- **Project tools vs Workspace Tools:** Pi's built-in tools (`bash`, `edit`, `write`, `read`, `grep`, `find`, `ls`) operate the project layer — the builder's repository — and run entirely inside the utility process. Space Zero Workspace Tools operate the app layer — Space Zero itself — and are registered as additional Pi custom tools whose `execute()` is a thin proxy that calls main over the `MessagePort`; the real handler, validation, safety policy, and Agent Activity History run in main. One Pi `AgentSession` carries both domains. The no-backdoors rule applies to Space Zero app internals, not to the user's project files.
- **Agent Definition scopes:** Definitions are discovered from four scopes — project (`<repo>/.agents/agents/`, walking up from a trusted Project Session cwd), spacezero (`<spaceZeroHome>/agents/`, following the user-configured Space Zero Home), user (`~/.agents/agents/`), and bundled (defaults shipped inside the app, e.g. a read-only `scout` researcher and a `reviewer`). On ID collision the most specific scope wins: project > spacezero > user > bundled. Global Settings has no Project Session identity, so it catalogs only spacezero, user, and bundled definitions; it never borrows a last-active project. Project definitions are contextual to a trusted Project Session. Unlike skills, definitions need no enable/disable toggle because they are chosen explicitly rather than loaded ambiently.
- **Agent Definition vs Session:** An Agent Definition is static configuration (a markdown file); a Session is a live workspace/runtime container with one current Chat Context. A definition may seed a session's model, thinking level, instructions, and tools, but the session remains a normal Space Zero Session afterwards.
- **Workspace Context vs Chat Context:** A stable workspace context owns durable tool and workspace state: the Global Chat context, the Knowledge Base context, or a Project Session worktree/source identity. A Chat Context owns one agent transcript and conversation memory. `/clear` rotates the current Chat Context without deleting or archiving the owning workspace context. `/resume` exposes older Chat Contexts tied to the current workspace context; choosing one makes that Chat Context current again and continues it in the same context/worktree.
- **No ordinary Workspace Sessions:** Space Zero has one Global Chat instead of user-created global Workspace Sessions. Users get freshness and history through `/clear` and `/resume`, not by creating multiple global sessions.
- **Multiple live chat contexts:** The utility process can hold multiple live agent runtimes concurrently. Multiple Project Sessions and chat contexts may run in the background; the active context is a UI focus concept, not a runtime limit. A resource cap on concurrent live runtimes is a tunable, not an architectural constraint.
- **Project Session isolation and source identity:** Every new Project Session uses a dedicated managed Git worktree; the registered Project path remains the base checkout. When an Issue or Pull Request starts a Session, SQLite stores the stable GitHub source identity and lightweight title/URL metadata, while Issue bodies, comments, diffs, checks, and reviews remain runtime-only.
- **Pi internals vs Space Zero source of truth:** Pi's `SessionManager`/`SettingsManager`/`DefaultResourceLoader` are used only inside the utility for the agent transcript and runtime config. Space Zero SQLite owns project/session/branch metadata and links to Pi transcript paths. Pi's broad default resource auto-discovery is not used for v0; Space Zero explicitly composes approved skill paths and tool composition through the SDK.
- **Managed workspace content vs application data:** Space Zero Home contains user-owned managed content such as projects, worktrees, knowledge, skills, and artifacts. Private application data such as SQLite, credentials, raw transcripts, logs, and caches stays in the OS application-data directory by default. Existing projects may remain at external paths and are registered rather than moved.
- **LLM auth/models vs app state:** LLM provider credentials and the model catalog are owned by Pi inside the utility (`auth.json`/`models.json` under the Space Zero agent dir), not mirrored in SQLite. The model catalog is workspace-global (one shared Pi `ModelRegistry`); each session selects its own model and thinking level. New sessions start from a workspace-global default model + default thinking level defined in Space Zero Settings; sessions may override both. Per-project default model/thinking is a v1 enhancement. OAuth is supported from day one via the OS browser + a `spacezero://` deep link routed through main. User-defined custom providers are deferred to a tracked enhancement issue but must be designed for.
- **Git CLI vs GitHub API:** Local repository operations should use the Git CLI. GitHub data and workflows should use Octokit.
- **Browser vs project preview:** Browser is one shared tabbed tool across Project Sessions, Global Chat, and Knowledge Base. A project preview is a normal Browser tab displaying a running project's URL, not a separate tool or mode; project association may add preview/debug affordances to that tab.
- **Browser vs external browser:** The integrated Browser keeps web content and project inspection near the agent workflow; opening a URL in the user's system browser remains a distinct action.
- **Command Palette vs command behavior:** The Command Palette is a human-facing discovery and invocation surface for App Commands. It should not own the implementation of command behavior.
- **App Sidebar vs Tool Pane:** The left App Sidebar owns app navigation and context selection. The right Tool Pane is a substantial split-view work surface beside chat; it hosts the active context's selected tool and is controlled by the Tool Switcher.
- **Tool Pane vs tool-internal layout:** The Tool Pane shows one active tool at a time. Selecting another tool replaces its contents; any tabs or secondary layout inside that content belong to the selected tool rather than to the Tool Pane.
- **Tool Pane configuration vs context implementation:** Project Sessions, Global Chat, and Knowledge Base use one standard Tool Pane shell rather than separate pane implementations. The shell receives contextual configuration containing stable tool identities, availability, roots, and capabilities, so tools can be added or adapted without rebuilding the pane.
- **Tool Pane context identity:** Tool Pane shell state is independent per stable workspace context: Project Sessions use their stable Session ids, Global Chat uses one stable global chat context key, and Knowledge Base uses one stable Knowledge Base context key independent of whichever Chat Context is current.
- **Collapsed Tool Pane vs Tool Switcher:** Collapsing the Tool Pane leaves the Tool Switcher as a floating vertical rail at the right edge. Choosing a tool opens the pane with that tool active, the vertical rail disappears, and the Tool Switcher appears horizontally inside the Tool Pane's own header. This is not the global Electron titlebar. The Tool Switcher's collapse action and the top-right pane toggle control the same state; reopening from the top-right restores the context's last active tool and width.
- **UI commands vs app-state commands:** App Commands can represent renderer-local UI/navigation actions or privileged app-state actions. Privileged or persisted actions must cross the preload/IPC boundary into main-process application services.
- **App Commands vs Workspace Tools:** App Commands are human-facing commands for the Command Palette, keyboard shortcuts, menus, and future human UI surfaces. Workspace Tools are agent-facing typed capabilities. They use separate registries, but app-state actions should converge on the same main-process application services.
- **Delegation tool vs Workspace Tools:** `agents.delegate` is a built-in Pi custom tool registered inside the utility process, not a Workspace Tool. Child-session spawning is agent-runtime work owned by the utility; routing it through main's Workspace Tool layer would be circular (utility → main → utility). The optional `spawns` frontmatter field controls which definitions a definition's child runs may delegate to (default: none — no nesting); `*` or a CSV list opts into nesting.
- **Workspace tools vs backdoors:** Agents should operate Space Zero through typed Workspace Tools that route into the same application services as the UI. They should not directly mutate SQLite, bypass IPC/application validation, or rely on brittle renderer UI automation for first-class app actions.
- **UI base vs agent runtime:** The agent UI base (shadcn Chat Components + AI Elements) is presentational only — components accept props and emit callbacks and do not bundle an agent runtime, transport, or backend. The renderer feeds them state from `window.spacezero.agent.*` IPC events brokered through main. assistant-ui's `@assistant-ui/react-pi` and CopilotKit couple to their own runtime/transport and are not used as dependencies; `react-pi`'s source is a reference pattern only (issue #48) for the Pi event → UI state projection.
- **Tool safety vs user autonomy:** Workspace Tools should declare safety levels such as read, write, and dangerous. Confirmation requirements are controlled by user settings so cautious builders can require approval while power users can allow dangerous actions without confirmation.
- **Skills vs Knowledge Base:** Skills are reusable behavioral instructions loaded on demand; the Knowledge Base stores durable user knowledge and documentation. Skills should not be silently copied into or managed as Knowledge Base content.

## Business and Product Rules

- Space Zero should optimize for reducing context switching for builders.
- v0 public builds are downloadable from a commercial website entry point and hosted through GitHub Releases, but installed app usage is gated by License Activation.
- Public onboarding order is Welcome, License Activation, GitHub connection, then optional Project setup.
- Beta users may receive free or fully discounted Polar-backed licenses; those licenses are still real entitlements and may later be deactivated or migrated into discounted renewal offers.
- When License Activation is expired, revoked, or otherwise invalid and the 7-day offline grace period has elapsed, public builds block workspace access and show a renewal/reactivation path rather than offering a read-only workspace mode.
- Normal updates remain user-controlled, but the license/version backend may mark a build unsupported for critical security, backend compatibility, or licensing reasons; unsupported public builds must block workspace access until updated.
- Keep release entitlement policy simple in v0: the desktop app should call one Space Zero backend status endpoint for License Activation and version support, returning license state, recheck/grace timing, supported/unsupported version policy, renewal/reactivation URL, and update/download URL when needed.
- Initial public release versions use SemVer prerelease identifiers on the beta channel, such as `0.1.0-beta.1`.
- Public macOS release artifacts must be built, Developer ID signed, notarized, and published by GitHub Actions rather than a local-only release process.
- Public beta releases are triggered by pushing a version tag such as `v0.1.0-beta.1`; the release workflow should verify that the tag matches `package.json` before publishing.
- GitHub Release notes are the canonical v0 release notes source for public downloads and update prompts; in-app rich release notes can be added later if needed.
- The commercial website should point macOS users to a signed/notarized DMG download, while the release may also publish ZIP/update metadata artifacts needed by the auto-updater.
- v0 macOS auto-update should use `electron-updater` with `electron-builder` and GitHub Releases rather than Electron's lower-level built-in `autoUpdater` directly.
- The app should favor a clean desktop GUI over terminal-first workflows.
- The v0 agent strategy is Pi-first; do not add multi-harness abstractions without a new decision.
- Electron is the v0 desktop shell because embedded browser/devtools capability and desktop process control matter more than a tiny binary.
- GitHub should be integrated deeply, not treated as a link-out-only experience.
- New projects and repositories created or cloned by Space Zero use `Space Zero Home/projects` by default. Existing repositories may remain at external paths and are registered without being moved. The Knowledge Base remains separate under `Space Zero Home/knowledge-base`.
- Knowledge Base image uploads use the fixed Knowledge Base-relative `assets/img/` directory and relative Markdown links; there is no attachment-location setting.
- The shared Files tool is a lightweight manual editing surface rather than a complete VS Code/Cursor workbench. Monaco through `@monaco-editor/react` is its shared code-editor engine, and Trees (`@pierre/trees`) is its renderer-only file explorer interaction and model foundation. Space Zero owns editor tabs, context isolation, dirty/save behavior, restoration, filesystem integration, and the privileged file-management services behind the explorer.
- The Files tree uses Trees' icon system with the broad built-in icon set and targeted Space Zero remaps only where product recognition requires them. Files uses Trees' compact density, enables sticky folders, derives Trees styling from Space Zero/editor theme variables where possible, and always compacts single-child directory chains using Trees' compact-folder behavior, so a path like `src/features/files/renderer` may appear as one navigable chain instead of several low-value intermediate rows. Within a directory, folders sort before files using natural case-insensitive ordering. v0 has one selected tree item at a time; multi-selection is deferred with bulk operations. The tree shows hidden and Git-ignored content but always hides and protects `.git` internals. For large trees, Files follows Trees' prepared-input guidance: main or another non-UI boundary loads canonical paths, applies Space Zero exclusions and ordering, and passes prepared or presorted input to the renderer rather than doing expensive tree shaping in UI code. Symbolic links appear as identifiable entries but v0 does not follow, expand, edit through, search through, rename, move, or trash them; Files exposes metadata and a reveal-in-system-file-manager action instead.
- Files uses a resizable and collapsible explorer column on the left and one editor group on the right. Explorer width and collapsed state persist independently per context. Explorer search has two modes: **Files search** is the default and filters the Trees explorer by canonical path/name inside the tree, while **Contents search** uses Space Zero's main-owned search service and replaces the tree with file/line/context match results. The editor remains usable while the explorer is collapsed.
- Files maintains an ordered multi-file tab set independently for each Tool Pane context, with one active editor. A single-click tree selection opens or replaces one clean preview tab; double-clicking, editing, or explicitly pinning the preview makes it permanent. Dirty tabs are permanent and are never replaced automatically. v0 uses one editor group with a horizontally scrollable tab strip: tabs retain readable widths, the active tab scrolls into view, and builders may drag tabs to reorder them. Split editor groups and side-by-side file editing are later enhancements.
- Files treats any valid UTF-8 content without binary markers as editable text regardless of filename extension. Monaco provides syntax support for recognized filenames and extensions and plain-text editing otherwise. Saving preserves an existing UTF-8 BOM and LF/CRLF line-ending convention rather than normalizing them silently; newly created files use UTF-8 without BOM and LF.
- Files limits Monaco and WYSIWYG editing to text files no larger than 2 MiB in v0. Larger files open as non-editable metadata views with an action to reveal them in the system file manager; the limit may become configurable later.
- Files previews PNG, JPEG, GIF, and WebP images up to the existing 10 MiB image limit. SVG remains editable text in Monaco rather than rendered as trusted image content. Other binary files and oversized images open as non-editable metadata views with a reveal-in-system-file-manager action.
- Files uses explicit save for every editable file, including Markdown/MDX in the WYSIWYG editor and supported text in Monaco. `mod+s` saves the active file, while a separate **Save All** action saves every dirty tab in the current Files context; saving a preview pins it. Save All reports failures per file and leaves failed tabs dirty. Save As is out of scope for v0. Files does not use timer-based or background autosave, and switching tools or contexts does not implicitly save. Dirty buffers remain in memory across tool and context switching. Closing a dirty tab requires Save, Discard, or Cancel; clean tabs close immediately, and save failures keep the dirty tab open with an actionable error.
- Files restores saved working state independently per context after app restart: permanent tab paths and order, active permanent tab, per-file editor mode, Monaco cursor/scroll view state, WYSIWYG scroll position, and expanded tree folders. Preview tabs remain in memory across tool/context switching during the current app run but are not restored after restart. v0 does not persist unsaved buffer content as recovery drafts. Normal quit or restart with dirty tabs requires Save All, Discard All, or Cancel; a crash or forced termination may lose unsaved edits. Hot-exit draft recovery is a later enhancement.
- Files provides two search modes within the active context root. **Files search** is the default explorer search mode and uses Trees' `hide-non-matches` mode to filter visible rows by canonical path/name. **Contents search** is explicit, routes through Space Zero's main-owned search service, respects `.gitignore` and common generated-directory exclusions by default, supports an **Include ignored files** option, always excludes `.git`, skips binary and files over 2 MiB, and opens results as preview tabs. v0 search is on demand without a persistent index.
- Files is a filesystem surface and shows read-only Git status decorations in both Project Session and Knowledge Base explorers through Trees' Git-like row signals. Files may also use Trees row annotations for critical filesystem policy markers that affect user action, such as symlink, protected/locked, or open-tab conflict states. Saving or mutating files only changes the active working tree; Files never stages, unstages, reverts, commits, checks out, or invokes other Git behavior. Git owns diff review, staging, recovery, commit, and branch workflows, and observes filesystem changes independently.
- Main-owned file watching and optimistic revisions detect external file modifications. A clean open tab reloads automatically; a dirty tab preserves its local buffer, enters a conflict state, and must choose **Reload from disk** or explicitly confirmed **Overwrite disk** before saving. v0 does not automatically merge external and local edits, and neither version is overwritten silently. If an open file disappears, its buffer remains open in a **Deleted on disk** state with explicitly confirmed **Recreate file** or **Close tab** actions. v0 treats external renames as deletion plus creation rather than guessing path identity, and refreshes the tree to show the new path.
- Project Session and Knowledge Base Files expose the same rooted file operations: create a file or folder, inline rename through Trees, move by Trees drag-and-drop or validated relative destination path, context-menu actions opened by right-click or a subtle row hover trigger button, move to the operating system Trash with confirmation, and reveal in the system file manager. Trees drag/drop is disabled while Files search is active. Files does not provide an Open in external editor action or preferred-editor setting. Trash failure never falls back silently to permanent deletion; an explicit permanent-delete action is a later enhancement. Rename, move, or trash affecting dirty tabs requires Save, Discard, or Cancel first. Successful rename or move rewrites affected open-tab paths and keeps them open; trash closes affected tabs only after the operation succeeds. These operations share a capability contract but always validate against the active context root in main. Copy/paste, duplication, bulk operations, and arbitrary file import are later enhancements.
- New sessions should start from a workspace-global default model and default thinking level defined in Space Zero Settings. A session may override both independently. Per-project default model/thinking is a v1 enhancement with project settings, not v0.
- LLM provider credentials and the model catalog are owned by Pi in the utility, not mirrored in SQLite. Renderer Settings/Model UI brokers to the utility through main over `window.spacezero`. OAuth providers are supported from day one via the OS browser plus a `spacezero://` deep link handled by main.
- Skills use `<Space Zero Home>/skills` as the native global location and also support `~/.agents/skills`, project `.agents/skills`, and project `.pi/skills`. Project skills take precedence over global skills after a persisted project-trust decision; without one, project-local skill discovery fails closed. The chat composer exposes available skills through `/skill:name` discovery while Pi owns command expansion. Settings provides global-skill enable/disable controls for the Space Zero Home and `~/.agents/skills` locations; disabled global skills are excluded from new or reloaded agent sessions, while project-local skills remain project-scoped.
- The chat composer slash surface lists both skills and chat commands in the same suggestion area. Chat commands such as `/clear` and `/resume` use a command-style icon to distinguish them from skills. Submitting `/resume` replaces the suggestion area with the current workspace context's Chat Context history list; each history row uses a `file-text` icon, shows a one-line truncated initial prompt as the primary label, and shows the Chat Context creation date/time as secondary text when available.
- Meaningful user actions should be implemented as application capabilities that can be reached by the renderer UI and, when appropriate, exposed as Workspace Tools for agents.
- Tool Pane open/collapsed state, width, and active tool persist across app restarts independently for each context. Tool-specific restoration such as open files, terminal lifecycle, browser history, and Git selection is defined by each tool's product contract rather than by the Tool Pane shell.
- A context with no saved Tool Pane state starts collapsed with the Tool Switcher visible. The first default tool is Files for Project Sessions and Knowledge Base, and Browser for Global Chat; saved context state takes precedence afterwards. Knowledge Base opens with Files visible by default.
- The Tool Pane is sized as a substantial split view rather than a narrow sidebar. Its initial width is approximately 60% of the workspace area beside the App Sidebar, it remains resizable, it should have roughly a 400px minimum, and it must preserve roughly 360px for chat instead of using a fixed maximum width.
- The Tool Pane shell uses the same background color as the primary chat surface. Tool-specific internal chrome and styling belong to each tool's own product contract.
- The initial Tool Pane supports collapsed and resizable split-view states only. Maximizing over chat, detached panes, and additional editor windows are later enhancements.
- Filesystem-backed Tool Pane tools receive context-specific initial roots. Project Session Files and Git are rooted in the Session's managed worktree, while its Terminal starts there. Knowledge Base Files and Git are rooted in the Knowledge Base repository, while its Terminal starts there. Global Chat Terminal starts in Space Zero Home. Browser has no filesystem root.
- A Terminal's context root is a validated starting directory and restoration fallback, not a filesystem sandbox. Shells run with the builder's normal operating-system permissions and may navigate anywhere those permissions allow without changing the owning Project Session, Global Chat, or Knowledge Base context. Files and Git remain confined to their separate context capability contracts.
- Each Tool Pane context owns an isolated collection of Terminal tabs. Opening Terminal creates its first tab lazily at the context's fixed initial root; builders may add, close, and switch tabs, but tabs never move between or inherit state from another Project Session, Global Chat, or Knowledge Base context.
- A Terminal tab's visible label is the basename of its last validated working directory and updates when shell integration reports a directory change; it falls back to the shell name when no directory label is available. v0 does not accept shell-controlled window-title sequences or provide manual tab renaming.
- In v0, each new Terminal tab launches the builder's configured operating-system shell. Space Zero does not provide custom shell profiles or per-tab shell selection. macOS and Linux use the user's configured shell, Windows uses PowerShell, and launch failures are reported with actionable guidance rather than silently choosing a different shell.
- Terminal shells run as normal interactive shells with the Electron main process's inherited environment and the user's standard shell startup behavior. Space Zero sets only terminal essentials such as terminal/color capability, the validated starting directory, and lightweight shell integration needed to report working-directory changes; it does not parse shell startup files, load project `.env` files, or inject project-specific secrets or variables. User-configured environment managers remain shell-owned.
- Each Terminal tab owns exactly one main-process PTY and remains bound to its owning Tool Pane context. Its process continues while the builder switches tabs, tools, or contexts or minimizes the app; hiding Terminal only detaches renderer presentation/subscriptions. The PTY ends when its command exits, the builder closes its tab, its owning context is permanently deleted, or Space Zero quits.
- Terminal processes do not survive or reconnect across an app restart, and Space Zero never replays their previous commands. On restart, every previously open tab is restored in its prior order as a fresh shell at that tab's last validated working directory, with the same active-tab selection and empty terminal output. Space Zero uses lightweight shell integration to receive current-working-directory updates rather than attempting to infer `cd` commands from terminal text. If integration is unsupported or a saved directory is missing or no longer valid as a launch directory, the tab falls back to that context's fixed initial root and reports the fallback.
- **Close Tab** is the only v0 terminal-termination action: closing a live tab requires confirmation, terminates its PTY/process tree, and removes the tab and its in-memory output. There is no separate Stop or Kill Terminal action. `Ctrl+C` remains ordinary terminal input. When a shell exits naturally, including through `exit` or `Ctrl+D`, Space Zero closes its tab automatically. If the last tab exits, Terminal remains open in an empty **New Terminal** state; it neither launches another shell nor collapses the Tool Pane. App quit and context deletion use one aggregate confirmation for affected live terminals rather than prompting once per tab. A global preference may disable these confirmations for builders who prioritize speed.
- Each Terminal tab keeps in-memory scrollback bounded by 10,000 lines or 5 MiB of retained output, whichever limit is reached first. Main retains the bounded output while the tab, tool, or context is hidden and replays it when the renderer subscribes again, so Terminal does not depend on inactive components remaining mounted. Reaching either limit discards the oldest output without stopping or throttling the PTY. Terminal output is not persisted to disk in v0 and is cleared on app restart because it may contain secrets.
- Space Zero v0 does not cap the number of Terminal tabs per context or live terminal PTYs across the app; builders are responsible for the processes they start. Output buffering remains bounded independently so runaway output cannot consume unbounded application memory.
- Terminal privilege remains in Electron main. The renderer receives opaque terminal ids and may request only typed create, subscribe, unsubscribe, input, resize, and close operations through `window.spacezero`; main resolves the configured shell, inherited environment, starting or restored directory, PTY, output buffer, and owning context. Main validates terminal and window ownership plus operation inputs, and streams output only to the owning Space Zero window. Embedded Browser content receives no Terminal IPC access.
- Typed Terminal IPC does not filter or approve commands entered by the builder. Once main has created the authenticated PTY, terminal input passes through unchanged and the shell may perform anything allowed by the builder's operating-system account. The boundary prevents renderer code from choosing an untracked executable, startup environment, or initial path; it does not turn the shell into a restricted command environment.
- Main persists Terminal tab metadata in SQLite: owning context, tab order, tab title, active-tab selection, and last reported working directory. Main validates persisted context and path data before restoring tabs as fresh shells and removes the metadata with its owning context. Live PTYs, terminal output, command history, and environment contents remain memory-only and are never persisted by Space Zero in v0.
- Switching away from Terminal preserves its running PTYs, active tab, and each tab's in-memory viewport and scroll position without changing cwd or creating tabs. Returning restores that state; switching contexts shows only the destination context's isolated tab collection. Restoring navigation does not move keyboard focus into Terminal unless the builder explicitly selects it.
- Only the visible active Terminal tab is fitted and resized to the current Tool Pane dimensions. Hidden and inactive tabs retain their last PTY dimensions until shown again. The renderer computes columns and rows with `@xterm/addon-fit` and sends bounded dimensions through typed IPC; main validates them before resizing the PTY.
- In v0, Terminal Links recognize web URLs in terminal output and require `mod+click`; ordinary clicks continue normal terminal selection behavior. A Terminal Link is navigation, not command execution: arbitrary output is never made click-to-run.
- Activating a Terminal Link opens its URL in a new Browser Tool tab in the same Tool Pane context and switches the pane to Browser without stopping the terminal. Returning to Terminal restores the same active tab and scroll position. If Browser is unavailable, Space Zero explicitly offers to copy the URL or open it in the operating-system browser; it never opens external content silently.
- The shared Git Tool is a read-oriented, AI-assisted review surface in both Project Sessions and the Knowledge Base. Background activity may refresh Git state, but must not stage files, create commits, pull or rebase, or push. The legacy Knowledge Base automatic sync behavior is replaced rather than carried into the shared tool.
- The Git Tool is diff-first: its main changes surface stacks file diffs with per-file headers rather than presenting only a compact status list. Text-file diffs are expanded by default, independently collapsible, and fold unchanged regions; binary or excessively large changes show a bounded summary instead of rendering excessive content. A changes selector defaults to **Uncommitted**, which shows all saved changes since `HEAD`; **Unstaged** shows working-tree changes outside the index, and **Staged** shows the index content Git would include in the next commit. Files and diff hunks are view-only: the initial tool has no file-selection checkboxes or direct stage, unstage, discard, commit, pull, rebase, or push mutations.
- The Git Tool includes a commit composer that routes the builder's commit instructions to the active agent Session rather than executing Git from renderer UI. Submitting the composer immediately sends a normal prompt through the Session's standard agent prompt path without reading, replacing, or appending to the primary chat draft; the request and response remain visible in the Session transcript. Composer text is optional: an empty composer asks the agent to choose an appropriate commit message, while entered text supplies the builder's preferred message or instructions. **Commit** is available when uncommitted changes exist; **Commit & Push** and **Commit and create a PR** are available when changes exist or the branch is ahead of its upstream, even when no remote is configured. In that case the agent may commit locally, explain why it cannot push, and ask the builder for the missing remote information in chat. **Commit and create a PR** reuses the commit-and-push flow, then uses authenticated GitHub tooling available to the Session, deterministically reuses an existing open pull request for the head branch when possible, and otherwise creates a non-draft pull request. Its final response includes the usable pull request URL; if the push succeeded but pull request creation failed, the agent reports that partial success and the actionable creation failure without claiming completion. During conflicts all three actions are replaced by **Resolve with agent**. Each shortcut asks the agent to inspect fresh repository state and handle the full workflow; the rendered diff is not copied into the prompt. A main-owned workspace-global Git setting chooses **Commit**, **Commit & Push**, or **Commit and create a PR** as the composer's visible primary action, defaulting to **Commit & Push**, while a small action menu offers the other choices for one request without changing the saved preference. The agent performs and explains staging, commit, remote, divergence, conflict, and pull request workflows through its existing project capabilities and authenticated tooling; Space Zero's GitHub credential remains main-owned and is not exposed to the renderer or project command environment. Git-originated prompts add no separate prohibition on discard, reset, or other Git operations; the agent follows the builder's instructions and the existing agent tool safety and confirmation policy. Git agent actions are disabled while the active agent is running; they do not interrupt the run or create a hidden prompt queue.
- When a repository has unresolved conflicts, the Git Tool shows a prominent conflict state and places conflicted files before other diffs. Conflict editing remains outside the Git Tool; **Resolve with agent** immediately sends a normal, transcript-visible conflict-resolution prompt to the active agent without changing the primary chat draft.
- The Git Tool shows a compact current-branch label and upstream divergence such as ahead/behind counts, without remote-management controls.
- The Git Tool refreshes when it becomes visible, while visible when repository changes are detected, when Space Zero regains focus, and when a Git-originated agent run finishes; it also provides manual **Refresh**. Refresh re-queries repository state rather than tracking a separate commit workflow and preserves the current changes filter, expanded-file state, and scroll position where the changed diff still permits it.
- Git Tool state is not restored across app restarts. Each restart queries fresh repository state and returns the tool to its defaults; filters, expanded files, scroll position, and unsent commit-composer text are session-only.
- Git owns diff review while Files owns file editing and save behavior. Activating a filename or changed line in a Git diff switches the Tool Pane to Files, opens the corresponding context-relative file, and positions the editor near that change. Git displays saved repository state only; it does not include or auto-save unsaved Files editor drafts.
- Git Tool renderer requests identify the active trusted context, never an arbitrary repository path. Main resolves and validates a Project Session's persisted managed worktree or the configured Knowledge Base repository, runs local Git queries, and returns typed status/diff data through preload IPC.
- Knowledge Base Chat receives narrowly scoped Knowledge Base Git Workspace Tools backed by main-process services so its agent can inspect state and fulfill staging, commit, remote-configuration, push, conflict, and other requested Git workflows under the existing tool safety policy. This does not make Git available to Global Chat. Project Session agents continue operating on their authenticated managed worktree through Pi project tools.
- Project Sessions and Knowledge Base expose Files, Git, Browser, and Terminal in the Tool Switcher. In both Files contexts, Markdown and MDX default to the existing WYSIWYG editor with an option to switch to Monaco source editing; both modes share one in-memory buffer and dirty state, and switching modes neither saves nor prompts. When the WYSIWYG editor cannot represent a document losslessly, Files keeps it in Monaco and explains why rich mode is unavailable. Other supported text files use Monaco. Global Chat exposes Browser and Terminal.
- Browser uses one shared multi-tab model in every context. General web pages and Project Session previews coexist as normal tabs; preview tabs do not create a separate Browser mode or Tool Pane tool and receive no automatic badge or localhost classification. Tabs use page title and favicon, falling back to hostname or URL. Each Project Session, Global Chat, and Knowledge Base context owns an isolated tab collection that must not leak into another context. A context with no saved tabs opens one blank new tab with its URL field focused; closing the final tab returns to that state rather than collapsing the Tool Pane or showing an empty tool. Tabs may be dragged to reorder, and their order is restored; pinned tabs, tab groups, and tab duplication are out of scope for v0.
- Browser preserves open tabs, the active tab, and each tab's last committed URL across app restarts. Full back/forward history is preserved only while the app is running; restored tabs start a fresh history stack at their saved URL. During an app run, tabs remain live while their Browser tool is hidden or the builder switches contexts, preserving page, form, media, and navigation state. Closing a Browser tab disposes that tab's live web content; permanently deleting its owning Session or Knowledge Base context removes all Browser state and live resources for that context. Ordinary navigation or archiving does not remove Browser state.
- After app restart, Browser restores tab metadata lazily. The active tab loads when its Browser context is first shown, and other tabs load when selected. A failed or unavailable URL remains in its tab with an error and retry action rather than being removed.
- Browser does not discover or scan for project dev servers. Builders open preview URLs manually or through explicit URL links and handoffs exposed by Space Zero.
- Chat links follow the workspace-global **Open chat links in** setting, which defaults to **Space Zero Browser** and also offers **Default browser**. Space Zero Browser opens the link in a new tab belonging to the same Project Session, Global Chat, or Knowledge Base context as the chat.
- Terminal URLs support an explicit `mod+click` handoff to a new tab in the Space Zero Browser belonging to the same context. This handoff always targets Space Zero Browser and does not use the chat-link opening preference.
- Browser v0 navigation chrome provides back, forward, reload/stop, an editable URL field, new tab, close tab, and **Open in default browser**. Reload becomes Stop while navigation is in progress. The URL field navigates recognizable URLs and localhost addresses directly and sends other text to Google Search. Home, bookmarks, and a downloads manager are not part of v0.
- Browser v0 provides standard focus-scoped shortcuts for focusing the URL field (`mod+l`), opening a tab (`mod+t`), closing the active tab (`mod+w`), reloading (`mod+r`), and platform-native back/forward navigation. They apply only when Browser is the active focused tool, resolve through stable command identities, and participate in the existing user-remappable shortcut system.
- Web content may not create uncontrolled Electron windows. An `http` or `https` link that requests a new window opens as a new Space Zero Browser tab in the same context. A supported non-web protocol such as `mailto:` is handed to the operating system only after user confirmation; malformed and unsupported protocols are denied.
- Every Browser download requires a native **Save As** choice. Dismissing the dialog cancels the download. Completion is reported through a lightweight notification with **Open** and **Reveal in folder** actions; v0 does not provide silent downloads or a persistent downloads manager.
- Sensitive web permissions are denied unless the builder approves an origin-specific prompt. v0 offers **Allow for this app run** or **Deny**; grants are not restored after restart. Camera, microphone, location, notifications, clipboard access, MIDI, and similar capabilities are never granted silently, and Chromium sandbox restrictions still apply.
- Certificate errors may be bypassed only for loopback URLs (`localhost`, `127.0.0.1`, and `[::1]`) after a clear **Proceed for this app run** warning. Browser never offers an invalid-certificate bypass for remote hosts.
- All Space Zero Browser tabs share one dedicated persistent browser profile across Tool Pane contexts. Its cookies, site storage, and authenticated sessions survive app restarts until the builder clears them. The profile is isolated from both the privileged Space Zero app renderer and the user's system-browser profile; temporary permission grants are not part of its restored state.
- Settings provides a confirmed **Clear Browser Data** action for the shared Browser profile's cookies, site storage, and cache. Clearing data applies across all contexts, retains saved tab URLs, and reloads live tabs into clean signed-out site sessions. Browser v0 does not store passwords or synchronize browser profiles.
- Every loaded page, including localhost project previews, remains sandboxed and receives no Node.js access or Space Zero preload API. Browser content cannot directly access the privileged app renderer. Any future inspection or debugging capability must use controlled Electron/Chromium facilities owned behind the main-process boundary rather than weakening page isolation. User-facing Developer Tools and integrated debugging UI are out of scope for Browser v0.
- Browser blocks script-created popups that are not caused by a user gesture. Ordinary user-initiated new-window links open as tabs, but authentication flows that require `window.opener` may use controlled temporary Browser child windows. Child windows share the dedicated Browser profile, retain the same sandbox, and close when the flow completes, the parent tab closes, or the app exits.
- Browser v0 is builder-operated. Agents cannot navigate tabs, inspect or interact with pages, or receive page content implicitly. Future agent-facing Browser Workspace Tools may build on approved main-process capabilities but require separate product and safety decisions.
- The Tool Switcher shows the full target tool set for its active context even during incremental delivery. Registered but unavailable tools remain visible as disabled, keyboard-inert controls labeled “Coming soon”; they cannot become or be restored as the active tool. If a context has no available tools yet, the Tool Pane remains collapsed and its top-right toggle does not open an empty pane.
- Tool Pane tool identities are stable and shared across contexts: `files`, `git`, `browser`, and `terminal`. Contexts configure which registered tools are available and how they operate; adding a future tool should extend the registry/configuration rather than require a new Tool Pane implementation.
- The Tool Pane owns context identity, available tools, active tool, open/collapsed state, and width. Each registered tool owns its own state and lifecycle; switching tools must not implicitly reset the previous tool, and the pane must not depend on keeping inactive tool components mounted. Tool-specific restart restoration belongs to each tool contract. If a saved tool is unavailable, the pane falls back to the context's default tool.
- The Command Palette should be a searchable mini Raycast-like UI inside Space Zero over the App Command Registry, not a place where command behavior is implemented directly.
- App commands should have stable IDs, user-facing titles, categories, optional search keywords, optional default keyboard shortcuts, and handlers or invocation targets.
- App commands may include both navigation/UI commands and app-state commands. Renderer-local UI commands may stay in renderer code; privileged or persisted app-state commands must go through `window.spacezero`, preload, typed IPC, and main-process application services.
- The Command Palette itself is renderer-owned UI. It owns presentation, search, keyboard interaction, and selection state, not privileged app behavior.
- The v0 App Command Registry should be generic to the app and does not need context-aware command availability. Context-aware commands, such as commands depending on the current project, session, selection, or focused panel, are a later enhancement.
- Workspace Tools should be designed as reusable internal application capabilities, but v0 exposes them only to the in-app Agent Workspace. External automation surfaces such as a CLI, MCP server, local socket, or public API are future possibilities, not v0 commitments.
- Space Zero has one user-facing session kind: **Project Sessions** (triggered from a Project and run in a dedicated managed worktree cwd). Global Chat and Knowledge Base Chat are stable workspace contexts rather than user-created Workspace Sessions. All three chat surfaces are built from reusable Chat Components and use rotatable Chat Contexts. Project Sessions use Pi's built-in project tools against the isolated worktree; Global Chat and Knowledge Base Chat primarily use Workspace Tools.
- Opening a configured, accessible Knowledge Base reuses the stable Knowledge Base workspace context across navigation and app restarts. It resumes the last current Knowledge Base Chat Context until the builder uses `/clear`; the previous Chat Context is retained for future history and a fresh Chat Context becomes current without inheriting conversation context. The chat may inspect registered Project sources and Knowledge Base content through approved application capabilities.
- Knowledge Base setup and repository recovery are temporary full-page states rather than chat contexts. The standard Knowledge Base Chat plus Tool Pane layout appears once its repository is configured and accessible.
- Workspace Tools should be grouped by product domain, matching feature areas such as workspace, projects, sessions, settings, and preview. Composed tools such as `workspace.getStatus` are allowed when they serve a clear product need, but teams should not create aggregate tools speculatively for every feature.
- Space Zero should keep a lightweight Agent Activity History for agent Workspace Tool calls. It should capture enough to explain what happened without becoming a heavy compliance audit system or storing sensitive full payloads by default.
- Keyboard shortcuts should be app-focused command accelerators in v0. They work when Space Zero is focused and should not use OS-global Electron `globalShortcut` registration for normal app actions.
- The Tool Pane foundation provides a **Toggle Tool Pane** App Command using `mod+shift+b`, replacing the old right-panel wording, and makes the Tool Switcher keyboard accessible. Individual tool commands and shortcuts are deferred to their tool PRDs and should invoke the shared Tool Pane controller rather than creating separate pane behavior.
- Keyboard shortcuts should resolve to stable App Command IDs rather than directly calling scattered callbacks. This follows editor-style command systems, where shortcuts, command palette entries, menus, and buttons can converge on the same command handler.
- Keyboard shortcuts should be user-remappable like VS Code/editor keybindings. The foundation should separate command identity, default keybinding, and user override keybinding.
- Keyboard shortcuts should support context-aware activation, similar to editor `when` clauses. The v0 implementation can start with simple context flags such as text input focused, modal open, command palette open, terminal focused, preview focused, or editor focused.
- Keyboard shortcuts should use a normalized cross-platform syntax such as `mod+k`, `mod+shift+p`, `alt+enter`, and `escape`. `mod` maps to Command on macOS and Control on Windows/Linux, while UI can render platform-native labels.
- Keyboard shortcut v0 should support single-stroke shortcuts only. Multi-step key chords such as `mod+k mod+s` are a future possibility, not part of the initial foundation.
- Keyboard shortcut event handling and shortcut resolution should live in the renderer because v0 shortcuts are in-app UI behavior. If a shortcut triggers app-state or native behavior, its command handler should use the normal preload/IPC/main application-service path rather than bypassing Electron security boundaries.
- An Agent Definition may be selected as a session persona only while a session is fresh (before its first prompt); the selection locks once the session starts, but the session may still override model and thinking level afterwards. When a definition is selected, its model and thinking level override the workspace-global defaults.
- Agent Definition discovery is lenient and diagnostic-driven: invalid global files are skipped with reasons surfaced in Settings, while project-file diagnostics belong to a trusted Project Session context; shadowed files are shown with their precedence status in the applicable catalog. Using a definition is loud: unknown models, empty tool allowlists, or reserved not-yet-supported fields (`output`, `blocking`) fail with explicit errors and never silently reinterpret the file's intent.
- Workspace Tool results should be structured data only. Agents are responsible for interpreting and summarizing tool results in conversation; tool results should not include polished human-readable summaries.
- Workspace Tools should be exposed through an explicit Workspace Tool Registry rather than ad hoc callable functions. The registry is the approved catalog passed to the agent harness, including tool names, input schemas, safety levels, and handlers.
- Each feature should own its Workspace Tool definitions near its main-process application services. The Agent Workspace or Workspace Control Plane composes feature-owned tools into the registry passed to Pi.
- Renderer IPC handlers, App Command handlers, and Workspace Tool handlers may be separate entrypoints, but app-state behavior must route into the same main-process application services for the underlying use cases.
- The App Command Registry and Workspace Tool Registry are separate catalogs because human-facing commands and agent-facing tools need different metadata, schemas, safety policy, and UX. They may converge on the same application services when they affect app state.
- Workspace Tools may include both domain/application actions and UI/navigation control actions. Tool metadata should distinguish UI control tools from app-state tools so safety policy, history, and agent instructions can treat them differently.
- UI-control Workspace Tools should still enter through the main-process tool layer. Main should validate, apply safety policy, record activity when appropriate, and then send typed UI commands/events to the renderer. Agents should not directly manipulate renderer internals.
